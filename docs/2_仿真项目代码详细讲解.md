# A3 双臂仿真项目代码详细讲解

> 本文从项目实际 Python 源码出发，解释模块结构、执行链路、关键实现和常见用法。源码根目录为 `AI305_Project_a3/a3_dual_arm_sim/`，以下代码路径均相对于该目录；章节中的文件行号可能随版本变化，应以函数名和代码内容为准。

## 1. 先建立整体认识

**这个仓库不是一个单独的机器人控制脚本，而是一套以 MuJoCo 环境为中心、可替换策略、可录制数据并能统一评测的实验框架。** 从程序视角看，至少有五层：命令行入口负责收参数，工作流负责组织一次或多次运行，策略负责由观测生成动作，仿真环境负责执行动作，任务模块负责判断任务进展和成功。

```text
命令行 / examples 脚本
        ↓
cli.py → workflows（运行、采集、评测、诊断）
        ↓                         ↘ data（可选录制）
Policy：专家 / 遥操作 / ACT / SmolVLA / 自定义插件
        ↓ Action
sim.env：校验、IK、关节限制、MuJoCo 物理步
        ↓ Observation + info
tasks：抓取/装盒状态、计数、槽位和成功判断
```

**首先要区分“物理执行”和“任务判分”。** `sim` 知道关节、接触、物体位置等仿真状态；`tasks` 把这些状态解释成“饼干在源盒还是目标盒、槽位是否填满、是否稳定成功”；`policies` 则只应通过约定的观测作决策，专家控制器是特例，可以经 `bind_env()` 读取仿真真值。

**代码使用 Gymnasium 风格环境接口，但真实项目还额外约定了动作模式、相机和数据格式。** 每回合的基本接口是 `reset(seed, options) -> (observation, info)` 和 `step(action) -> (observation, reward, terminated, truncated, info)`。控制周期通常包含多个 MuJoCo 物理子步，因此一次 `step` 不等于一次物理积分。

## 3. 从命令行进入代码

**`a3-sim` 的第一站是 `cli.py`，它解析命令，但大多数业务实现在 `workflows/cli_handlers.py`。** 例如 `a3-sim run` 的参数在 `cli.py:parser()` 定义，随后 `main()` 取出 `args.function` 并调用 `_run(args)`；`_run` 再加载插件、创建环境、构造 `EpisodeRunner` 并启动回合。

```python
# src/a3_dual_arm_sim/cli.py 的结构示意
run = commands.add_parser("run", help="Run a replaceable Python policy plugin")
run.add_argument("--policy", required=True, help="Python module:factory")
run.set_defaults(function=_run)

# main() 的统一分发
args = argument_parser.parse_args(argv)
exit_code = int(args.function(args))
```

**复杂流程通常有两类入口：稳定的 `a3-sim` 通用命令，以及专门实验的 `examples/` 或 `workflows/*_cli.py`。** 通用入口适合 inspect、smoke、run、teleop、replay；装盒专家采集、2×10 任务和模型评测由专用 CLI 配置任务参数。选择入口时先确定要执行的是“单策略运行”“成功数据采集”还是“标准 benchmark”，不要把它们当成可互换的命令。

## 4. 模型构建：URDF 到 MuJoCo

**`sim/model.py` 在运行时把机器人与场景拼装为 MuJoCo 模型。** `build_model(config, scene)` 先解析 A3 URDF 获得 link/joint 信息，再建立 MJCF XML 树，配置物理参数、地面和桌面、灯光相机、左右臂关节链、夹爪以及任务物体，最终编译成 `MjModel` 并返回包含模型、XML 和关节映射的 `ModelBundle`。

```python
# sim/model.py 的核心流程（略去具体 XML 属性）
urdf, source_joints = _source()
root = ET.Element("mujoco", model=f"a3_dual_arm_{scene}")
# 由 config 设置 timestep、重力、接触参数和资源
world = ET.SubElement(root, "worldbody")
# 递归建立左右机械臂的 link/joint 链
add_chain(base, source_joints[LEFT_JOINTS[0]], "left")
add_chain(base, source_joints[RIGHT_JOINTS[0]], "right")
# cookie_transfer 场景再加入源盒、目标盒和饼干
```

**URDF 与运行时 MuJoCo 模型各司其职。** `assets/a3/source/A3.urdf` 提供机器人关节、连杆和惯性等来源信息；`sim/urdf.py` 解析它；`sim/robot_builder.py` 将连杆、碰撞/视觉几何和 Robotiq 夹爪转成 MJCF 结构；`sim/object_builder.py` 建立桌面、盒子和饼干。`models/` 中已有 XML 可用于检查/生成产物，但核心构建逻辑在 `sim/model.py`，并不只是加载一个固定 XML。

**场景配置不是任务判分器。** YAML 和 `config.py` 控制相机、家位、步长、噪声、几何尺寸等参数；而“放入多少块算成功”由 `tasks` 中代码判断。改几何参数不应被误认为改变了成功标准，反之亦然。

## 5. 仿真环境与控制周期

**`A3DualArmEnv` 是控制策略与 MuJoCo 之间的适配层。** 在 `sim/env.py` 初始化阶段，它加载配置、调用 `build_model()`、缓存关节/执行器/相机/传感器 ID、建立动作空间与观测空间，并按需创建笛卡尔动作的 IK 适配器。

**一次 `reset()` 会清物理状态、设置双臂家位、随机化对象并做短暂稳定。** Gymnasium 的随机数生成器由 `seed` 管理；可用 `options` 关闭通用物体随机化。环境随后设置夹爪、执行若干 MuJoCo 步使初始状态稳定，时间归零后生成第一帧观测。

**一次 `step(action)` 会先校验，再将动作归一到 16D 关节目标，然后受限执行多个物理子步。** 若输入是 14D `cartesian_delta`，环境用 `CartesianDeltaAdapter` 做 IK；若输入是 `joint_position`，目标直接进入关节限位和限速环节。之后执行 `config.substeps` 次 `mujoco.mj_step()`，期间监控 NaN/Inf 和异常速度，最后返回新观测及请求动作、实际动作和安全原因等 `info`。

```python
# sim/env.py 的 step() 主干（概念化）
requested = validate_action(action, mode)
canonical = requested if mode == "joint_position" else self._ik.convert(...)
applied = self._limit_joint_action(canonical)
self._apply_controls(applied)
for _ in range(self.config.substeps):
    mujoco.mj_step(self.model, self.data)
observation = self._observation()
return observation, 0.0, terminated, truncated, info
```

**`applied_action` 比策略原始输出更接近实际执行事实。** 安全限位、动作速率限制和 IK 都可能使策略请求值发生变化；`info["requested_action"]` 是传入动作，`info["applied_action"]` 是被环境规范化/限幅后实际下发的关节目标。训练数据采集和评测诊断应明确记录是哪一种，不可把模型原始预测说成 MuJoCo 实际执行动作。

**安全终止和步数截断表达不同含义。** `terminated=True` 常见于 safety stop；`truncated=True` 表示达到环境 horizon。benchmark 自己还有 `max_steps` 上限，所以“环境没 safety terminate”也不等于 episode 成功。

## 6. 观测、动作和策略接口契约

**跨模块最重要的公共约定集中在 `contracts.py`。** 它规定左右臂各 7 个关节、关节名称/顺序、16D 关节动作、14D 笛卡尔动作、观测字典键名以及动作和观测的基本有效性检查。

| 名称                          | 形状/约定             | 解释                                              |
| ----------------------------- | --------------------- | ------------------------------------------------- |
| `observation.state`         | 16                    | 左 7 关节 + 左夹爪 + 右 7 关节 + 右夹爪           |
| `observation.velocity`      | 16                    | 同顺序的关节/夹爪速度                             |
| `observation.eef_pose`      | 14                    | 左右末端各 3D 位置 + 4D 四元数                    |
| `observation.force`         | 18                    | 双腕力/力矩、指尖触觉及夹爪执行器力               |
| 三路 `observation.images.*` | `H×W×3 uint8 RGB` | 前视、左腕、右腕相机                              |
| `joint_position` action     | 16                    | 绝对关节目标，角度单位 rad，夹爪 0 关/1 开        |
| `cartesian_delta` action    | 14                    | 每臂 6D 归一化位姿增量 + 1D 夹爪，范围 `[-1,1]` |

**模型输出形状正确还不够，动作含义也必须匹配。** `joint_position` 不是速度或增量；将一个 14D 笛卡尔动作误交给 16D 关节模型接口会失败或造成错误语义。环境通过 `action_mode` 选择动作解释，策略插件也必须声明同一属性。

**插件的最小接口是 `reset`、`act`、`close` 和 `action_mode`。** `policies/base.py` 用 `Protocol` 描述接口，`load_policy("module:factory")` 动态导入模块并调用零参数工厂。`reset(EpisodeContext)` 用于清理上回合状态；`act(observation, task)` 每个控制周期返回一个动作；`close()` 释放模型、GPU 等资源。策略若是规则专家，可额外实现 `bind_env(env)`，但读取物体真值会让比较不再是纯视觉策略。

```python
class MyPolicy:
    action_mode = "joint_position"

    def reset(self, context):
        self.target = None

    def act(self, observation, task=""):
        if self.target is None:
            self.target = observation["observation.state"].copy()
        return self.target.copy()

    def close(self):
        pass

def make_policy():
    return MyPolicy()
```

**8D 左臂模型要由适配器补成环境所需的 16D 控制动作。** 内置 SmolVLA 检查点可输入/输出 8D 左臂，`smolvla.py` 在 reset 后保存环境观测中的右臂 8D 状态，并在推理后拼接回来；右臂不是补零，也不是每步读取真值并追随。自定义插件若实现 8D 模型，必须自行做同样的维度适配。

## 7. 策略执行与工作流

**通用单回合工作流由 `EpisodeRunner` 管生命周期，策略不负责重置环境或判定成功。** `cli_handlers._run()` 先通过插件工厂得到策略，再基于其 `action_mode` 创建环境，创建可选录制器，最后将环境、策略、任务文本和录制器交给 runner。runner 每个控制周期大致执行：策略生成动作 → 环境 step → 保存动作前观测和实际应用动作 → 检查策略结束/环境终止/步数上限。

**benchmark 在通用 runner 之上增加可重复的多 episode 评估。** `make_cookie_benchmark(task=...)` 根据 `2x5` 或 `2x10` 选择 benchmark 类型；`evaluate()` 按连续 seed 运行 episode，支持专家并行 worker，收集逐回合 `EpisodeScore`，再汇总成功率、平均分、步数和时间。学习模型通常单进程评测；专家策略可并行。

**`EpisodeExecution.run_episode()` 是理解评测细节的关键位置。** 它选择 seed 对应的来源列、构造任务提示、创建/重置环境、绑定或重置策略、启动录制/诊断，然后在循环里调用 `act()` 和 `env.step()`。回合结束后，除了环境 `success`，还会检查目标盒数量、源盒余量和安全原因，生成结构化失败原因并决定保存或丢弃采集 episode。

**有些 benchmark 的“主分数”和“任务 success”并不是同一个指标。** 统一 cookie benchmark 记录 `cookies_in_target` 数量作为 score；`success` 仍要求完整环境规则满足。2×10 可计到最多 20 块，2×5 最多 10 块。比较实验时要按照对应 CLI/文档明确的排名指标阅读结果，不要只看一个布尔成功字段或中途最大计数。

## 8. 装盒任务判定：为什么不只是数饼干

**任务成功判定属于环境侧的 `tasks/cookie_transfer.py`，不会由策略自报。** `A3CookieTransferEnv` 继承物理环境，维护源盒、目标盒、饼干和槽位的 MuJoCo ID；其 `step()` 先执行父环境物理步，再根据每块饼干当前位置、姿态、速度和接触/几何规则重新计算任务状态。

**一块饼干“在目标盒内”需要几何和运动状态符合约束。** `_cookie_inside_target()` 把 cookie 位置变换到目标盒局部坐标，结合饼干旋转后的包围范围检查是否越过内壁、是否在地板与墙高之间，并检查倾斜程度、相对目标盒速度和角速度；可配置的释放要求还会检查手指接触。

**完整 2×5 填充会同时检查数量、源盒数量、槽位占用、四边覆盖和稳定保持。** `_target_slot_occupancy()` 将饼干与目标槽位做一对一匹配；`_collection_touches_all_walls()` 检查整组饼干覆盖到盒子的边缘范围；完整条件连续满足 `success_hold_steps` 步才置 `success=True`。这避免饼干短暂飞过盒内、堆叠错误或刚好碰到目标区域就被算作成功。

**2×10 不是把 2×5 的容量数字改成 20 就结束。** 它有专用的 `tasks/cookie_2x10.py`、计划/设置模块、专家和执行工作流，使用四次抓取计划 `[n, 10-n, n, 10-n]`，还会验证每列释放数量等任务规则。CLI 会选择匹配的场景配置和专家；避免只替换几何却复用错误任务计分器。

## 9. 专家控制器和遥操作

**规则专家是人工编写的闭环状态机，而不是训练出来的神经网络。** `controllers/` 中专家会利用 `bind_env()` 获得仿真对象位置、夹爪接触等 privileged 信息，选择目标饼干并执行接近、抓取、抬升、搬运、放置、释放和恢复等阶段。`phases.py` 集中声明阶段枚举，专家子类针对同列、变列、批量和 2×10 任务扩展策略。

**阅读复杂专家时从“状态枚举 + act 主循环 + 阶段处理函数”入手。** 不要从数百行的坐标常量开始逐行硬读；先找到当前 phase 的分派逻辑，再追踪进入/退出条件、每阶段的目标位姿、夹爪设置和失败恢复。专家中的真值访问是刻意设计的老师/基线能力，不等于模型获得相同输入。

**遥操作也是一种策略插件，只是动作由键盘控制面板提供。** `controllers/teleop.py` 把按键事件转成 14D 笛卡尔增量；`teleop_panel.py` 管理按键持续、选臂、夹爪和运行线程；`cli_handlers._teleop()` 创建 `cartesian_delta` 环境并启动 viewer。若要录制相机数据，不能关闭 policy camera rendering；桌面 viewer 和策略观测相机是不同功能。

## 10. 数据录制、采集和审计

**`data/recording.py` 把通用环境帧转为 LeRobot v3 数据集。** `Recorder` 协议使 runner 不依赖具体存储格式；`MemoryRecorder` 用于内存测试，`LeRobotV3Recorder` 写磁盘数据。每帧保存三路图像、state、velocity、eef pose、force、动作和任务文本；数据动作使用 canonical 16D 关节目标。

**标准专家采集器和通用 `a3-sim run --record` 的语义不同。** 专用 cookie 采集会运行专家、完整检查任务成功，并只将符合要求的 episode 正式保存，同时记录尝试日志和随机化/任务元数据；通用 recorder 更适合调试插件轨迹，不自动保证成功筛选，也不生成完整的标准采集摘要。不能把任意策略跑出来的数据直接宣称为通过专家成功审计的数据集。

**采集链路的质量关由数据审计模块实现。** `audit.py` 和对应 CLI 会读取 LeRobot 元数据、A3 sidecar 和任务约定，检查成功标签、动作维度、任务类型以及特定任务的抓取计划/释放记录。2×10 审计要求计划与记录彼此吻合，不应手工补造摘要绕过审计。

**只在训练需要时才做 16D 到 8D 左臂转换。** `prepare_left_arm_dataset_cli.py` 创建独立输出，把 state/action 投影为左臂维度并维护数据引用；原数据应保留。训练和评估必须使用对应维度及正确统计量/processor，不能把 8D 与 16D 检查点混用。

## 11. ACT / SmolVLA 训练与部署

**模型训练代码负责准备训练器和数据契约，推理插件负责把检查点接到共同策略接口。** `learning/` 管理基座/数据准备、训练命令与检查点处理；`policies/act.py`、`policies/smolvla.py` 实现在线推理。运行普通仿真不需要导入 Torch/LeRobot，相关依赖在使用训练或模型插件时才加载。

**SmolVLA 插件的核心是严格复用检查点配置与 processor。** 初始化时读取检查点配置、检查输入和动作维数是否为匹配的 8D/16D、载入权重和前后处理器；`predict_action()` 只负责模型原始动作预测，`act()` 再进行右臂保持、可选锚定/后处理等部署规则。调试时要分别看 raw action、后处理动作和环境 applied action。

**ACT 使用动作块时要区分预测长度与每轮实际执行长度。** `chunk_size` 是单次预测的动作序列长度，`n_action_steps` 是重新推理前消费的步数；它们影响控制延迟和纠错频率。时间集成会融合跨时刻预测，项目接口对其参数有约束，应以 `docs/act.md` 和 CLI 校验为准。

**检查点必须和训练时的数据统计、处理器及维度配套。** SmolVLA 的 `checkpoint_bundle.py` 负责查找/补齐处理器与训练相关配置；ACT 评测还需要匹配的数据集元数据。模型文件存在不等于可正确部署，推荐先跑短训练/短评测，再进行完整评估。

## 12. 常用命令与用法

**源码模式下先安装项目，再运行 `a3-sim` 或 Python 模块。** 推荐 Python 3.12；以下 Bash 命令适用于 Linux。Windows PowerShell 不使用 `MUJOCO_GL=egl command` 这种前缀方式，应先在 PowerShell 中设置环境变量，或按桌面渲染模式运行。

```bash
python -m pip install -e '.[dev]'
a3-sim --help
a3-sim inspect --scene cookie_transfer
MUJOCO_GL=egl a3-sim smoke --scene cookie_transfer --steps 20
```

**跑 benchmark 时要明示任务、策略、随机化条件、seed、步数和结果文件。** 下面是一个小规模 2×5 专家评测例子；`--episodes 1` 只用于验证执行链路，正式对比应使用足量 episode 和固定协议。

```bash
MUJOCO_GL=egl python examples/benchmark_cookie_batch.py \
  --task 2x5 --policy expert --profile basic \
  --episodes 1 --seed-start 1000 --workers 1 \
  --max-steps 500 --output outputs/expert_smoke.json
```

**自定义策略通过 `module:factory` 加载，工厂必须可被 Python 导入且不需要参数。** 先用保持初始姿态的策略验证接口、相机键和维数，再替换成模型推理；示例策略位于 `src/a3_dual_arm_sim/examples/custom_policy.py`。

```bash
a3-sim run --scene cookie_transfer \
  --policy a3_dual_arm_sim.examples.custom_policy:make_policy \
  --task "transfer 10 cookies into target box" --steps 100
```

**数据采集先小批量验证录制和审计，再投入训练。** 下面只示范 2×5 的专家成功数据采集入口；2×10 要用其独立的场景、随机化配置和采集脚本。

```bash
MUJOCO_GL=egl python examples/collect_cookie_benchmark.py \
  --randomization-config configs/randomization.yaml \
  --episodes 5 --max-attempts 15 --seed-start 6001 \
  --root datasets/cookie_2x5_trial --repo-id local/cookie-2x5-trial

python examples/audit_smolvla_data.py \
  --root datasets/cookie_2x5_trial --repo-id local/cookie-2x5-trial \
  --output outputs/cookie_2x5_audit.json
```

**模型推理、训练和评测依赖可选组件与本机权重，不应把示例路径当作仓库内自带文件。** 具体 SmolVLA/ACT 参数、GPU 配置、续训和检查点选择见仓库 `docs/workflow_guide.md`、`docs/smolvla.md`、`docs/act.md`。

## 13. 结果、诊断与调试顺序

**定位失败时先区分接口错误、物理执行问题、任务规则问题和策略能力问题。** 接口错误常见于动作维数/模式不匹配；执行问题看 `requested_action` 与 `applied_action`；物理问题看接触、速度、安全终止和截图；任务规则问题看目标计数、槽位占用、源盒数量和 `unmet_success_conditions`；策略问题再结合完整 trace 分析。

**推荐的最短调试闭环是 inspect → smoke → 单 episode 专家 → 数据/模型小测 → 多 seed 评测。** 先验证资源可加载，再验证环境有限状态正常，然后验证任务专家与成功判定，接着验证训练数据和模型接口，最后进行统计性比较。跳过前面的检查会让训练失败和仿真配置错误混在一起。

**日志和诊断轨迹应记录配置上下文而不只记录分数。** 统一 benchmark JSON 有汇总和逐回合信息；诊断目录可记录视频、动作、阶段和任务计数。建议同时保存任务版本、seed、随机化 profile、策略检查点、prompt、动作块设置和最大步数，才能复现实验并解释性能差异。

## 14. 测试代码怎么读

**测试文件基本按模块职责命名，是理解契约和回归边界的最快补充材料。** 例如 `test_env.py` 测 reset、限速、安全停止和相机；`test_model.py` 测 MuJoCo 模型资源/关节/夹爪；`test_cookie_2x10.py` 测计划、随机性、放置和成功条件；`test_contracts.py` 测动作维数和范围；`test_runner_and_recording.py` 测策略接口和 LeRobot 录制。

**看到实现细节不确定时优先找对应测试，而不是从测试推断整个行为。** 测试展示的是已经锁定的局部期望，模块代码和文档才说明完整执行链路。修改环境动作契约、任务判分或录制格式时，要同时跑对应测试以及必要的集成测试。

```bash
python -m pip install -e '.[dev]'
python -m pytest tests/test_contracts.py tests/test_env.py
python -m pytest tests/test_cookie_2x10.py tests/test_benchmark.py
```

## 15. 关键文件的建议阅读顺序

**按一条策略动作从输入到输出的路径阅读，比按文件名从上到下更有效。** 建议先用以下顺序建立骨架，再根据研究问题深入专家、模型或数据模块。

1. `contracts.py`：明确 observation/action 的键、维度和类型。
2. `config.py` + `configs/cookie_batch.yaml`：理解场景参数从哪里来。
3. `sim/model.py`、`sim/robot_builder.py`、`sim/object_builder.py`：理解模型如何生成。
4. `sim/env.py`、`sim/actions.py`：理解 reset、step、IK、安全限制和观测。
5. `tasks/cookie_transfer.py`、`tasks/cookie_2x10.py`：理解任务状态与成功条件。
6. `policies/base.py`、`workflows/runner.py`：理解策略插件如何执行。
7. `controllers/*expert.py` 或 `policies/smolvla.py`：按研究对象深入具体策略。
8. `workflows/episode_execution.py`、`workflows/benchmark.py`：理解统一评测和记分。
9. `data/recording.py`、`data/collection.py`、`data/audit.py`：理解演示数据如何产生和验证。
10. `learning/`：在确定输入输出契约后，再读模型训练与检查点处理。

## 16. 最容易混淆的边界

**启动成功、episode 结束、benchmark 得分和任务成功是四种不同的事实。** 程序可正常启动但策略失败；episode 可因超时结束；数量得分可大于零但完整成功标志仍为 false；任务成功还受稳定、槽位和边界等约束。

**专家真值、策略观测和诊断信息不能混成同一种输入。** 规则专家读取仿真内部位置/接触信息是允许的专家设计；模型纯视觉评测只应使用其契约规定的相机、关节和任务输入；诊断可以额外记录真值，但不应把它偷偷传入模型形成信息泄漏。

**请求动作、模型动作、环境应用动作必须分别命名。** 策略插件可以做后处理，环境也会做 IK、限位和限速；比较或训练时要说明使用的是哪一阶段的动作，优先用环境给出的 `applied_action` 代表真正下发目标。

**2×5、2×10 的几何、采集、提示、专家和判分应成套匹配。** 2×5 是两批各 5 个的十块任务；2×10 是四批、总计 20 个且计划/释放规则不同。跨任务跑模型可以作为迁移实验，但不能称为它已经针对目标任务完成训练或验证。

**仿真参数的功能性可用不等于真实机器人标定。** 模型几何、关节驱动、接触和相机能支持软件实验，但项目文档明确提示并未完成真实硬件标定；仿真成功率不能直接外推成实体机器人成功率。

## 17. 总结

**理解代码的主线是“统一契约把策略、环境、任务、数据和评测连起来”。** 配置与模型构建定义场景，环境把动作变成物理状态变化，任务模块解释状态，工作流管理 episode 和评分，录制器把时序转成训练数据，学习插件则将模型接入相同执行接口。

**做代码修改时应把改动放回正确的职责层，并用对应测试验证。** 物理结构改 `sim`/模型资源，输入输出改 `contracts` 和策略适配，任务成功条件改 `tasks`，专家行为改 `controllers`，采集/数据格式改 `data`，实验编排改 `workflows`。这种边界能减少改一处却悄悄改变评估协议的风险。
