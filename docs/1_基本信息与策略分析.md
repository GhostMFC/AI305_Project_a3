# 双机械臂机器人策略模型优化项目：基本信息与初步策略分析

> 本文根据 `midterm.pdf`、项目仓库 README 以及仓库 `docs/` 中的项目说明整理而成。它的目标是帮助我们先把项目“是什么、怎么运行、如何评价、接下来怎么优化”讲清楚，再进入具体的 Coding Agent 开发和实验阶段。

## 1. 项目一句话概括

我们要研究的是：

> **能否让 Coding Agent 自动分析机器人策略模型的失败原因，修改模型/训练/数据/部署配置，运行有限次数的实验，并通过 MuJoCo 闭环仿真结果不断迭代，从而提高双机械臂完成装盒任务的成功率。**

这里有三个关键词：

- **双机械臂**：环境中有左、右两条机械臂，每条机械臂有 7 个关节和 1 个夹爪控制量。
- **策略模型**：给定相机图像、关节状态等 Observation，预测下一步或未来一段时间要执行的 Action。项目中已有规则专家、ACT、SmolVLA 等策略。
- **闭环仿真**：模型的动作会真正送进 MuJoCo 环境，环境状态会因此变化，再把新的观察返回给模型。模型不能只在静态数据上预测得好，还要连续完成抓取、搬运、释放和稳定装盒。

项目地址：[https://github.com/Eter0109/a3_dual_arm_sim](https://github.com/Eter0109/a3_dual_arm_sim)

## 2. 课程项目的阶段目标

### 2.1 中期阶段重点

中期阶段**不要求已经训练出性能提升的模型**。本阶段重点是证明我们理解了项目，并且能够设计出后续可执行的优化方案。需要完成的事情可以归纳为四类：

1. **熟悉并跑通项目**：阅读 README 和 `docs/`，理解环境、任务、数据、策略接口和评估流程，至少跑通一次基础仿真或已有策略评估。
2. **调研机器人策略方法**：至少调研 3 种相关方法，说明输入、输出、动作生成机制、优点、局限和可尝试的优化方向。
3. **调研 Coding Agent / ML Agent**：至少调研一种 Agent，理解它如何读代码、改代码、运行实验和根据结果反思。
4. **设计 Agent 驱动的优化闭环**：明确目标指标、可搜索空间、工具、失败分析、实验记忆、计算预算以及人与 Agent 的分工。

因此，中期汇报的核心不是“我们已经把模型做到多强”，而是：

> **我们是否理解了真实项目，并提出了一个可验证、可记录、受预算约束的后续优化计划。**

### 2.2 最终要解决的问题

后续项目要通过实验回答：

> 在有限的训练和评估预算下，Coding Agent 是否能够通过“分析 → 假设 → 修改 → 训练 → 评估 → 反思 → 再迭代”的闭环，提升机器人策略的闭环任务性能？

这要求最终结果不仅包括模型权重，还要包括：实验命令、数据版本、配置、随机种子、评估协议、失败轨迹和每轮修改原因。否则无法判断性能变化究竟来自模型改进、数据变化、部署参数变化，还是评估条件变化。

## 3. 项目环境和任务是什么

### 3.1 MuJoCo 双臂仿真环境

项目基于 MuJoCo 物理仿真。MuJoCo 负责模拟：

- 双机械臂的运动学和动力学；
- 关节、夹爪、盒子和饼干之间的接触；
- 相机观察；
- 动作执行后的状态变化；
- 任务是否满足成功条件。

仿真环境的优点是可以反复 reset、改变随机布局、批量运行实验，不需要真实机器人硬件就能测试策略。但也要注意：项目 README 明确说明，仿真的几何、动力学、相机和夹爪参数是功能性默认值，尚未完成真实硬件标定。因此，仿真成功不能直接等价于真实机器人部署成功。

### 3.2 核心任务：把饼干从源盒转移到目标盒

项目的主要任务是单盒装盒任务：将源盒中的饼干转移到目标盒中。项目说明中给出的批次场景通常是：

- 源盒中有 80 块饼干；
- 目标盒容量为 10 块；
- 目标是将指定的 10 块饼干放入目标盒；
- 双臂可以分别承担抓取、扶盒、搬运或协作动作；
- 批次场景控制频率为 20 Hz，底层物理频率为 1000 Hz。

项目中还有同列、跨列、协作等不同专家场景。不同场景的饼干编号、布局和机械臂协作方式可能不同，不能把某一个固定布局的成功直接当成所有随机布局都成功。

### 3.3 规则专家、ACT 和 SmolVLA

当前项目已经提供多种策略或策略接口：

| 策略     | 主要输入                     | 基本特点                                                        | 在项目中的作用                       |
| -------- | ---------------------------- | --------------------------------------------------------------- | ------------------------------------ |
| 规则专家 | 仿真位置、接触等真值         | 通过人工设计的状态机决定抓取、移动、释放和恢复                  | 作为可运行基线、数据采集器和上限参考 |
| ACT      | 相机图像、关节状态           | 从演示数据学习动作序列，通常采用 Action Chunk，一次预测一段动作 | 代表行为克隆/动作序列策略            |
| SmolVLA  | 三路相机、关节状态、任务文本 | 视觉-语言-动作模型，根据图像、状态和任务描述预测动作            | 代表 VLA 类策略和多模态输入          |

规则专家可以读取仿真真值，所以它与只看相机和关节状态的学习模型不完全公平。规则专家的主要用途是验证环境和生成成功演示；真正比较学习策略时，要明确输入是否包含额外真值。

## 4. 一条策略完整执行链路

最重要的理解是下面这条闭环：

```text
环境状态
  ↓
Observation：图像、关节状态、速度、末端位姿等
  ↓
Policy：规则专家 / ACT / SmolVLA / 自定义模型
  ↓
Action：绝对关节目标或笛卡尔位姿增量
  ↓
动作校验、IK、限位、限速
  ↓
MuJoCo 执行多个物理步
  ↓
新的环境状态和任务诊断信息
  ↓
成功判定 / 失败原因 / 下一次 Observation
```

更具体地说：

1. 环境在一个控制周期开始时产生 Observation。
2. 策略根据 Observation 和任务信息计算 Action。
3. 项目会检查动作的维度、数值是否有限、是否越界，并进行必要的逆运动学转换、关节限位和限速。
4. 环境执行处理后的动作。策略预测的动作和环境实际应用的动作可能不完全相同，因此评估和数据记录应优先关注 `info["applied_action"]`。
5. 任务模块检查饼干是否抓取、是否释放到盒内、是否稳定、是否满足完整排布等条件。
6. 如果任务没有结束，环境返回新的 Observation，策略继续预测。这就是闭环，而不是只调用一次模型。

## 5. Observation、State 和 Action 规则

### 5.1 Observation / State

项目的常见观测包括：

| 观测                               |            形状 | 含义                                                 |
| ---------------------------------- | --------------: | ---------------------------------------------------- |
| `observation.state`              |       `(16,)` | 左臂 7 个关节位置、左夹爪、右臂 7 个关节位置、右夹爪 |
| `observation.velocity`           |       `(16,)` | 双臂关节和夹爪状态变化率                             |
| `observation.eef_pose`           |       `(14,)` | 两个末端执行器各自的 3D 位置和 4D 姿态四元数         |
| `observation.force`              |       `(18,)` | 力反馈，具体排列由环境实现定义                       |
| `observation.images.front`       | `H×W×3` RGB | 前方相机图像                                         |
| `observation.images.left_wrist`  | `H×W×3` RGB | 左腕部相机图像                                       |
| `observation.images.right_wrist` | `H×W×3` RGB | 右腕部相机图像                                       |

对于视觉学习模型，通常重点使用三路图像和关节状态。规则专家则可以额外使用仿真真值，但这种信息不能偷偷注入需要进行纯视觉评估的学习模型。

### 5.2 Action

项目支持两种重要动作空间：

#### A. 16 维绝对关节目标 `joint_position`

排列为：

```text
[左臂 7 个关节, 左夹爪, 右臂 7 个关节, 右夹爪]
```

- 关节值是绝对目标位置，单位为弧度；
- 夹爪值位于 `[0, 1]`，其中 `0` 表示关闭，`1` 表示张开；
- 它不是关节增量、速度或力矩，不能把其他动作空间的输出直接当成绝对关节目标。

#### B. 14 维笛卡尔增量 `cartesian_delta`

每条机械臂包含 6 个归一化位姿增量和 1 个夹爪指令，共 14 维：

```text
[左臂位置/姿态增量 6 维, 左夹爪 1 维,
 右臂位置/姿态增量 6 维, 右夹爪 1 维]
```

所有值位于 `[-1, 1]`，环境再通过 IK 将其转换成可执行的关节目标。使用模型时必须确认模型输出的动作空间、维度、归一化方式和当前部署接口完全匹配。

### 5.3 8D 左臂模型和 16D 双臂模型

数据和模型有两种常见模式：

- **16D 模型**：完整预测左右两臂的状态/动作。
- **8D 左臂模型**：只观察和预测左臂的 7 个关节加夹爪，部署时右臂不能简单补零，而应保持 reset 后首次观测得到的右臂目标。

这一区别是后续实验中非常容易出错的地方。使用 8D 数据训练的模型不能直接按 16D 模型的方式部署；需要明确截取左臂观测、拼接右臂保持目标，并记录数据统计量和处理器来源。

## 6. 任务成功不是“程序没报错”

一次运行正常只说明程序启动、策略返回了合法动作，不能说明任务成功。任务成功由环境侧的任务模块判定，通常需要同时满足：

- 达到规定的入盒数量；
- 饼干位于目标盒有效范围内；
- 位置满足目标槽位容差；
- 姿态和速度满足要求；
- 满足完整槽位占用和四侧边界覆盖等布局条件；
- 这些条件连续保持若干控制步，而不是瞬间经过一次。

默认 benchmark 的关键阈值包括：

- 目标数量为 10；
- 连续保持成功条件 5 个控制步；
- 控制频率 20 Hz，因此 5 步约为 0.25 秒；
- 槽位中心容差约为 `x ± 15 mm`、`y ± 5 mm`；
- 整组边界覆盖容差为 30 mm。

阈值可以通过命令行参数调整，但不同阈值对应不同评估协议。报告必须记录 `run.success_conditions`，否则不同实验的成功率不可直接比较。

应当区分以下指标：

| 指标                    | 能说明什么                             | 不能说明什么                           |
| ----------------------- | -------------------------------------- | -------------------------------------- |
| 训练 loss               | 模型是否在训练目标上拟合               | 不能直接说明闭环任务成功               |
| Teacher-forced 动作误差 | 在给定真实历史时，动作预测是否接近示范 | 不能反映误差累积和分布外状态           |
| 入盒数量                | 搬运效果的粗略分数                     | 不能替代完整成功判定                   |
| 完整闭环成功率          | 在固定评估协议下完成任务的比例         | 仍受随机种子、布局和仿真真实性影响     |
| 失败轨迹诊断            | 失败发生在哪一步、违反了哪些条件       | 需要结合轨迹和可视化，不能只看一个总分 |

## 8. 初步策略模型分析

### 8.1 规则专家：先作为基线和数据教师

规则专家利用仿真位置、接触等真值，通常通过状态机完成“选择饼干 → 接近 → 抓取 → 搬运 → 释放 → 恢复”。它的优势是：

- 不需要训练，容易快速跑通；
- 行为可解释，失败位置比较容易定位；
- 可以生成成功演示，用于 ACT 或 SmolVLA 的行为克隆训练；
- 可以帮助验证任务成功判定和 benchmark 流程。

它的局限是：

- 依赖仿真真值，不代表真实相机输入下的能力；
- 规则可能只适合固定布局或少数场景；
- 专家轨迹的多样性不足时，学习模型容易过拟合；
- 如果专家本身无法处理接触扰动，模型会学习到相同的脆弱行为。

初步结论：规则专家不应只被当作“竞争对手”，更应被当作环境 sanity check、成功数据生成器和失败分析参照。

### 8.2 ACT：适合从成功演示学习连续动作

ACT 的核心思想是从观测直接预测一段未来动作，即 Action Chunk，而不是每次只预测一个动作。这样可以减少动作抖动，并让抓取、搬运和释放等短期动作具有连续性。

需要重点理解的时序参数：

- `chunk_size`：一次预测包含多少个动作；
- `n_action_steps`：重新推理前实际消费多少个动作；
- 在 20 Hz 下，执行 8 个动作约等于 0.4 秒；
- `num_steps` 若出现在 flow 推理设置中，指推理迭代次数，不是训练步数。

ACT 的潜在优点：

- 适合演示数据驱动的操作任务；
- Action Chunk 能表达一小段连贯操作；
- 相比大型 VLA，模型和训练流程可能更容易控制；
- 可以先从左臂 8D 任务开始，降低实验复杂度。

局限和风险：

- 行为克隆会累积误差，进入训练数据之外的状态后可能失控；
- chunk 太长时，遇到抓取失败或布局变化不容易及时纠正；
- chunk 太短时，动作可能变得抖动，推理开销也增加；
- 演示数据覆盖不足会使模型只记住固定路径。

初步可尝试的优化方向：调整 chunk 和重预测频率、增加成功轨迹的布局多样性、加入失败恢复数据、比较动作平滑与及时纠错之间的影响。

### 8.3 SmolVLA：适合研究视觉-语言-动作输入

SmolVLA 使用三路相机、关节状态和任务文本等信息生成动作。它的价值在于能够研究多模态输入对机器人操作的帮助，例如任务文本是否能够区分不同搬运目标，腕部相机是否有助于抓取和放置。

潜在优点：

- 可以同时利用视觉、状态和语言条件；
- 可能比纯状态策略更能处理视觉变化；
- 适合研究不同相机、任务描述和数据规模对策略的影响。

局限和风险：

- 输入预处理、processor、数据统计和部署配置较复杂；
- 模型较大，训练和推理成本可能高于 ACT；
- 多相机时序、图像视角和任务文本不一致会产生隐性误差；
- 训练 loss 下降不一定转化为闭环成功率提升。

初步可尝试的优化方向：审计三路图像与状态数据、检查 processor 和归一化、对比相机组合、优化任务文本、加入恢复/纠错示范，并用闭环 trace 判断模型究竟是“看错了”“抓不住”还是“放置不稳定”。

### 8.4 Diffusion / Flow-based Policy：适合作为后续调研方向

Diffusion Policy 或 Flow-based Policy 不是当前仓库中必须立即实现的模型，但属于课程要求允许调研的机器人策略方法。它们通常不是直接输出一个确定动作，而是从噪声或简单分布逐步生成动作序列。

可能的优势：

- 能表达多峰动作分布，同一个目标可能存在多种合理轨迹；
- 对复杂连续动作和多步轨迹有较强表达能力；
- 可以与 Action Chunk 结合。

主要代价：

- 推理有多次去噪或 flow 迭代，实时性和计算成本更高；
- 训练和超参数更多；
- 生成的动作仍然需要符合本项目的 8D/16D 接口和动作约束。

初步建议是先把 ACT 或现有 SmolVLA 闭环流程跑通，再根据失败模式判断是否真的需要引入 Diffusion/Flow，而不是仅因为方法先进就直接扩大系统复杂度。

### 8.5 方法的初步选择

按照“风险低、可解释、能形成实验闭环”的顺序，建议：

1. **规则专家作为环境和数据基线**：先确认场景、成功判定和轨迹记录都正确。
2. **ACT 作为优先优化对象**：接口相对清晰，适合快速进行 chunk、数据多样性和恢复示范实验。
3. **SmolVLA 作为多模态策略对照**：重点研究相机、任务文本、processor 和部署参数，而不是盲目调大模型。
4. **Diffusion/Flow 作为方法扩展**：只有在确认当前失败确实来自单峰动作表达能力不足时再投入。

## 9. Agent 驱动的初步优化方案

### 9.1 推荐闭环

后续 Coding Agent 可以按照下面的工作流运行：

```text
Analyze
  ↓ 分析代码、配置、日志、轨迹和历史实验
Hypothesize
  ↓ 提出一个可验证的失败原因和改动假设
Implement
  ↓ 修改限定范围内的代码、数据处理或训练配置
Train
  ↓ 在预算内训练或短跑验证
Evaluate
  ↓ 用固定协议进行闭环 benchmark
Reflect
  ↓ 分析成功率、失败阶段和副作用
Iterate
  ↓ 记录结果并决定下一轮实验
```

关键原则是**每轮只验证一个主要假设**。如果一轮同时换模型、换数据、换动作空间和换成功阈值，即使结果变好，也很难知道真正原因。

### 9.2 Optimization Objective：优化什么

第一目标建议是：

> 在固定场景、随机化范围、最大步数、控制频率和成功判定下，提高完整闭环任务成功率。

辅助指标可以包括：

- 平均入盒数量；
- 达到首次抓取、首次入盒和完整成功所需的步数；
- 抓取失败、漏放、碰撞、出盒、超时等失败类型比例；
- 动作抖动、越界动作和恢复次数；
- 多个随机 seed 上的平均值和方差。

不要把训练 loss 单独作为最终优化目标。它可以用于诊断训练过程，但最终模型要在环境闭环中验证。

### 9.3 Search Space：允许 Agent 改什么

为了控制风险，建议分层开放搜索空间：

| 层级           | 可修改内容         | 例子                                                             |
| -------------- | ------------------ | ---------------------------------------------------------------- |
| 第一层：低风险 | 推理和部署参数     | `chunk_size`、`n_action_steps`、动作平滑、最大步数、相机组合 |
| 第二层：中风险 | 数据和训练参数     | 数据采样、成功/恢复轨迹比例、学习率、batch size、训练步数        |
| 第三层：高风险 | 模型和接口         | 网络结构、动作表示、8D/16D 模式、训练目标、策略插件代码          |
| 禁止自动修改   | 评估公平性相关内容 | 成功阈值、任务判定逻辑、随机化协议、历史结果文件                 |

Agent 不应通过降低成功阈值或改变 benchmark 协议来制造虚假的性能提升。若确实要研究阈值影响，必须作为单独实验并显式记录。

### 9.4 Tools：Agent 可以使用什么

Agent 可以使用：

- 文件读取和代码搜索工具，定位策略、环境、任务和训练入口；
- Shell 命令运行 `inspect`、`smoke`、训练、评估和数据审计；
- 日志、JSON、JSONL trace 和 episode 视频/截图分析工具；
- Git diff 或实验快照，记录每轮代码改动；
- 固定的评估脚本和结果汇总脚本。

最重要的不是让 Agent 拥有无限权限，而是给它**边界清晰、输出格式固定的工具**。例如评估工具应返回成功率、失败类别、seed、配置摘要和诊断路径，而不是只输出一段自然语言。

### 9.5 Failure Analysis：如何分析失败

建议把失败按任务阶段分类：

1. **感知/定位失败**：没有正确识别目标或末端位置。
2. **接近失败**：机械臂没有到达合适抓取姿态。
3. **抓取失败**：夹爪没有夹住、接触不稳定或碰撞导致目标掉落。
4. **搬运失败**：动作轨迹不稳定、碰到其他物体或超出安全范围。
5. **释放失败**：饼干没有进入目标盒，或放置位置不满足槽位要求。
6. **稳定/排布失败**：数量达到要求，但没有连续保持、边界覆盖或完整布局不满足。
7. **恢复失败**：前一步失败后，策略无法重新规划。
8. **系统失败**：动作维度错误、归一化错误、processor 不匹配、超时或渲染/资源问题。

诊断时应同时查看：最终成功标记、`unmet_success_conditions`、每步 `trace.jsonl`、动作前观测、实际应用动作、关键阶段截图以及随机 seed。只看最终分数无法确定应修改模型、数据还是部署配置。

### 9.6 Experiment Memory：实验记忆

每次实验至少记录：

```text
experiment_id
parent_experiment_id
修改假设
代码版本和 dirty diff
数据集路径与 revision
模型检查点路径和 hash
场景、随机化、seed、最大步数
动作空间、8D/16D 模式、processor
训练配置和计算时间
成功率、入盒数量、失败类别
trace/诊断文件路径
Agent 的反思结论和下一步建议
```

这样 Agent 才能避免重复尝试失败配置，也能判断一次性能提升是否可复现。建议每个实验使用独立的 `outputs/<run>` 目录，不覆盖旧结果。

### 9.7 Compute Budget：限制实验成本

可以采用分阶段预算：

- **阶段 A：静态检查**：只做代码、数据和配置审计，不训练。
- **阶段 B：短训练**：少量步数验证代码和 loss 是否正常。
- **阶段 C：小规模闭环**：少量 episode、固定 seed，快速筛除明显失败方案。
- **阶段 D：正式评估**：只有通过前面门槛的候选才运行更多 episode 和随机 seed。

每轮设置最大训练步数、最大运行时间、最大 episode 数和最大磁盘空间。Agent 若连续若干轮没有改进，应停止搜索并总结原因，而不是无限调参。

### 9.8 Human-in-the-loop：人与 Agent 的分工

建议由人负责：

- 确定任务目标、评估协议和公平比较原则；
- 审批高风险代码和模型结构修改；
- 判断仿真结果是否具有研究意义；
- 决定最终采用哪条方法路线。

建议由 Agent 负责：

- 阅读和定位代码；
- 生成实验假设；
- 执行低风险修改和标准化实验；
- 整理日志、轨迹和失败分类；
- 维护实验记忆并提出下一轮候选。

Agent 的角色不是“自动随意改代码”，而是一个受约束的实验工程师。它应该能够解释每次改动对应的假设和证据。

## 10. 初步研究问题和可执行实验

中期之后可以优先做以下几组实验：

| 实验问题                        | 自变量                                | 主要指标                 | 预期意义                         |
| ------------------------------- | ------------------------------------- | ------------------------ | -------------------------------- |
| Action Chunk 是否影响闭环稳定性 | `chunk_size`、`n_action_steps`    | 成功率、动作抖动、超时率 | 判断连续动作和及时纠错的平衡     |
| 数据多样性是否改善泛化          | 固定布局 vs 多布局、多 seed、恢复数据 | 随机 benchmark 成功率    | 判断模型是否只记住单一路径       |
| 三路相机是否都必要              | 前视、腕部相机组合                    | 抓取/放置失败率          | 定位视觉信息瓶颈并降低推理成本   |
| 8D 左臂策略是否足够             | 左臂预测 + 右臂保持 vs 16D 双臂       | 协作场景成功率           | 判断任务是否真正需要双臂联合学习 |
| 失败恢复是否有效                | 只训练成功数据 vs 加入恢复示范        | 中途失败后的恢复率       | 验证闭环策略的鲁棒性             |
| Agent 反思是否带来有效搜索      | 人工调参 vs Agent 闭环                | 单位预算的性能提升       | 验证课程项目的核心假设           |

每个实验都要保持其他条件尽量一致，并在报告中说明改变了什么、为什么改变、结果是否支持原假设。

## 11. 中期汇报建议结构

可以按以下顺序组织汇报：

1. **项目背景和目标**：双臂 MuJoCo、饼干装盒任务、策略优化问题。
2. **系统和执行链路**：Observation → Policy → Action → Environment → Evaluation。
3. **任务规则和接口**：状态/动作维度、8D/16D、成功条件和评估指标。
4. **基础运行过程**：使用 Coding Agent 阅读代码、运行冒烟测试和规则专家，说明遇到的问题。
5. **策略方法调研**：规则专家、ACT、SmolVLA，再加至少一种 Diffusion/Flow/VLA/World Model 方法。
6. **方法比较**：输入、输出、动作生成机制、优势、局限和优化方向。
7. **初步选择**：为什么优先尝试 ACT 或 SmolVLA，为什么暂不直接扩大模型复杂度。
8. **Agent 设计**：Analyze → Hypothesize → Implement → Train → Evaluate → Reflect → Iterate。
9. **实验管理**：搜索空间、失败分析、实验记忆、预算和人机分工。
10. **后续计划**：先跑通基线，再做小规模对照，最后进行多 seed 正式评估。

## 12. 当前最重要的注意事项

- “冒烟测试通过”不等于“任务完成”。
- “程序没有报错”不等于“策略成功”。
- 入盒数量不等于完整任务成功率。
- 固定布局专家结果不能直接代表随机 benchmark 结果。
- 8D 左臂模型的右臂不能补零，应保持 reset 后的右臂目标。
- 必须确认模型动作空间是绝对关节目标还是笛卡尔增量。
- 必须使用与检查点匹配的 processor、数据统计和数据根目录。
- 训练 loss、离线动作误差和闭环成功率必须分开报告。
- 改变成功阈值、随机化方式或控制频率后，结果不能与原协议直接混比。
- 仿真参数没有真实硬件标定，仿真提升不能直接宣称真实机器人提升。
- Agent 的每次修改都应有明确假设、独立实验记录和可复现结果。

## 13. 总结

这个项目的本质不是单纯训练一个机器人模型，而是建立一个可靠的机器人策略实验闭环：

1. 先理解 MuJoCo 环境、双臂接口和装盒成功规则；
2. 再比较规则专家、ACT、SmolVLA 以及其他策略学习方法；
3. 然后设计一个受约束的 Coding Agent，使它能够分析失败、提出假设、修改代码或训练配置、运行闭环评估并记录实验；
4. 最后用固定协议、多 seed 和失败诊断判断 Agent 是否真的提高了任务成功率。

中期阶段最合理的成果是：**一个讲得清楚、跑得起来、评估公平、后续可以继续执行的优化方案**。模型性能提升属于后续实验目标，而不是中期汇报必须提前完成的结果。
